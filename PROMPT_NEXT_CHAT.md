Предыдущий исполнитель менял код и запускал локальные проверки. Пользователь результат не принял. Не считай эти жалобы закрытыми. Точная текущая ошибка и точная версия, опубликованная после последнего архива, не подтверждены. Сначала воспроизведи сбой и проверь, какой код реально загружается в браузер. Не утверждай, что причина найдена, по одному предположению.

В этом архиве:
- `project/` — последняя переданная версия проекта, из архивной версии 23;
- `source/` — сохранённые исходники прежнего публичного сайта;
- этот файл — актуальная постановка задачи; старые отчёты внутри проекта содержат исторические сведения и местами противоречат друг другу.

Архив восстановлен из файла eduard-firebase-source-checkpoint.zip, версия 23. Контрольная сумма исходного архива: SHA-256 e77efad7d9af2723e9cfab023687b16985713e36c461b79c395b5ddbe9b6a32f. Сам новый архив с этим промптом имеет другую сумму.

## Что нужно сделать

### 1. Доказательно исправить загрузку песни

Пройди весь путь: вход владельца → доступ Google Drive → проверка папки → создание resumable upload → передача и подтверждение размера файла → серверная проверка Worker → запись media и tracks в Firestore → появление в каталоге → воспроизведение оригинала и отображение обложки на публичном сайте.

Найди конкретный неработающий этап по Console/Network и безопасным ответам API. Не проси присылать access token, private key, полный HAR с Authorization или токены ботов. Показывай пользователю понятную ошибку, этап и код ответа. Не скрывай исключение сообщением «готово».

Проверь актуальность JS/CSS, версию Worker, настройки сборки, scope OAuth, права на папку, CORS, Firestore rules и доступ reader к именно новому файлу. Это направления проверки, а не установленные причины.

Ранее была ошибка `Failed to execute 'fetch' on 'Window': Illegal invocation`. В архиве уже есть исправление вызова native fetch через Reflect.apply в DriveUpload. Нужно проверить, выполняется ли этот код в реальном браузере, и нет ли аналогичных вызовов в других местах.

Повтор после сетевого сбоя не должен создавать несколько одинаковых песен и файлов. Конвертация дополнительных MP3 не должна мешать публикации рабочего оригинала. Нельзя объявлять материал опубликованным до успешного сохранения метаданных.

### 2. Сделать подключение Диска понятным и максимально автоматическим

Пользователь не хочет после каждого F5 заново входить и выбирать ту же папку. Сейчас в исходниках browserSessionPersistence для Firebase и кратковременный OAuth access token в sessionStorage для Drive; это НЕ постоянный доступ и не полноценное обновление Google access token.

Раздели состояние входа Firebase и состояние разрешения Google Drive. Проверь восстановление после F5, закрытия/открытия вкладки и истечения доступа. Разработай корректное восстановление/обновление доступа в рамках выбранной архитектуры. Если Google требует первое согласие или новый жест пользователя, объясни это прямо; не обещай бесконечный доступ. Не сохраняй пароль Google и не переноси секреты в браузер.

Папка публикаций уже задана. Не заставляй выбирать её при каждом действии. Не делай весь Drive публичным и не расширяй права сервисного аккаунта без необходимости.

### 3. Полностью переделать UX/UI админки

Оба предыдущих варианта дизайна пользователь отверг. Смена цвета или очередной набор вкладок задачу не решают. Самостоятельно предложи и реализуй цельный, аккуратный интерфейс для владельца музыкального сайта.

Основной сценарий должен быть очевиден: «Добавить песню» → аудиофайл → название и обложка → наглядный предпросмотр → одна основная кнопка публикации. Автоматически заполнить то, что можно достоверно получить из файла; всё должно оставаться редактируемым. Не выдумывай автора или данные релиза.

В списке материалов нужны видимая обложка, название, дата, статус, прослушивание, редактирование и управление видимостью. Покажи понятные состояния загрузки, прогресс, успех, отмену и повтор. Убери технический мусор и лишние конкурирующие кнопки из основного сценария. Для неполной настройки дай понятный статус и действие. Нужны удобные desktop и mobile, доступные подписи и отсутствие горизонтального переполнения.

Перед финальной передачей проверь интерфейс в разрешённом браузерном окружении. Покажи реальный скриншот, если такая проверка доступна. Не выдавай текстовое описание или mock-DOM тест за визуальную проверку.

### 4. Довести публикации в Telegram

Сейчас нужны только два Telegram-канала. VK отложен по прямому указанию пользователя, не настраивать и не блокировать из-за него запуск.

Требования: выбор одного/двух каналов; текст/подпись; прикрепление картинки либо видео; локальный предпросмотр; явная кнопка отправки после проверки; история и отдельный результат для каждого канала. Не связывай вложения Telegram с повторным подключением Диска.

В архиве уже реализован multipart путь через Worker и sendPhoto/sendVideo, но реальная отправка вложения не подтверждена. Проверь существующую реализацию, не создавай параллельный несовместимый механизм. Текущие ограничения приложения: JPG/PNG до 10 МиБ, MP4 до 20 МиБ, подпись со ссылкой до 1024 символов. Это ограничения исходников, не заявление обо всех текущих лимитах Telegram API; при изменении сверяй официальную документацию.

Сохрани проверку владельца на сервере, ограничения тела и типов файлов, защиту от повторной отправки и различие «отклонено»/«результат неизвестен». Никогда не отправляй автоматический повтор, если предыдущая отправка могла пройти. Не отправляй реальные тестовые посты без явного выбора пользователем текста, вложения и канала.

## Архитектура и точки входа

- Firebase Hosting + Firebase Google Auth + Firestore.
- Браузер загружает файлы в Google Drive от лица владельца через drive.file.
- Cloudflare Worker читает закрытый Drive через отдельный reader, проверяет публикацию в Firestore, отдаёт медиа и выполняет публикации Telegram.
- Apps Script обслуживает отправку заявок по почте; Turnstile проверяется на Worker.
- Общую архитектуру не меняй без технической причины. Firebase Spark/бесплатный режим. Не включай Blaze и платные услуги.

Основные файлы:
- `project/web/admin.html`, `admin.css`, `admin.mjs` — интерфейс и контроллер;
- `project/web/admin-media.mjs` — DriveSession и предпросмотр;
- `project/web/drive-upload.mjs` — resumable upload;
- `project/web/quality.mjs`, `quality-worker.js` — дополнительные MP3;
- `project/web/social-composer.mjs` — редактор Telegram;
- `project/worker/src/index.mjs` — маршруты, CORS, verify и выдача медиа;
- `project/worker/src/google.mjs`, `http.mjs` — серверный Google-доступ и запросы;
- `project/worker/src/social.mjs`, `social-media.mjs`, `social-targets.mjs` — отправка, multipart и площадки;
- `project/tools/build.mjs`, `rollout.mjs`, `project-config.mjs` — сборка и развёртывание;
- `project/firestore.generated.rules`, `firebase.json`, `package.json`;
- `project/tests/` — существующие проверки;
- `project/DEPLOY.md`, `SETUP.md`, `UPDATE-WINDOWS.txt` — предыдущие инструкции.

Изменять нужно исходники в web/, а не только сгенерированные копии в public/. Сборка копирует их в public/. В архивном `public/js/cloud-config.js` есть пустые workerOrigin, pickerApiKey и turnstileSiteKey: это результат сборки без локальных настроек. Это не доказательство, что такие же значения опубликованы на сайте пользователя. Нельзя выкладывать этот public/ вслепую вместо сборки с его рабочей конфигурацией.

## Проверка и выдача результата

Сначала прочитай package.json и реализацию скриптов. Основные команды в существующем проекте:

```bat
cd /d "C:\eduard-site\project"
npm run doctor -- --strict
npm test
npm run build -- --draft
npm run check
npm run bundle:worker
npm run test:runtime
npm run test:hosting
```

При изменении правил дополнительно нужны соответствующие тесты. Не запускай seed, массовые изменения каталога и реальные рассылки для диагностики.

Порядок развёртывания последнего обновления был:
```bat
npm run deploy:worker -- --apply
npm run smoke
npm run deploy:hosting -- --apply
```
Это справка о существующих скриптах, а не поручение выкладывать непроверенный архив. Пользователю нужны точные команды для итогового исправления, по одной, с остановкой при ошибке.

Критерии приёмки:
1. Реальная MP3/WAV с обложкой сохраняется и появляется на сайте; можно воспроизвести оригинал.
2. Сбой дополнительного кодирования не скрывает сохранённый оригинал.
3. F5 не теряет действующее подключение; истечение доступа обработано понятно.
4. Ошибка указывает фактический этап и не создаёт ложный успех/дубликаты.
5. В интерфейсе понятно, как добавить, найти, прослушать и отредактировать материал; обложка видна.
6. Для Telegram доступны картинка/видео, предпросмотр, выбор канала, явная отправка и корректные результаты по каналам; повтор не дублирует пост.
7. Проверены desktop/mobile и актуальность реально опубликованных файлов.
8. Существующий каталог, закрытый доступ к Drive и серверные секреты сохранены.

Работай последовательно до готового результата. Не отправляй очередную косметическую правку под видом завершённой работы. В финале дай: точную найденную причину с доказательством; что изменено; что реально проверено; что ещё нельзя подтвердить; полный архив обновления без секретов; короткие команды установки. Если реальный E2E нельзя проверить в доступном окружении, прямо напиши «Я не могу это подтвердить» и обозначь конкретный недостающий шаг.
