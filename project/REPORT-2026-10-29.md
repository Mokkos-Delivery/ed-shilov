# Studio 4: изменения и проверка от 29.10.2026

Релиз: `2026-10-29-studio-4`. Внесены изменения в исходники, собран и проверен проект.
Продакшен не обновлялся. DNS, существующий каталог, Drive-права и серверные секреты не менялись.

## Что удалось установить

Точную причину пользовательского сбоя на действующем сайте установить нельзя: чтение сайта и Worker отклонено сетевым прокси среды с `403 Forbidden`, а авторизации владельца и серверных учётных данных здесь нет. Архив не доказывает, какая версия сейчас опубликована.

В исходниках воспроизведены и исправлены конкретные дефекты:

1. **Неопределённый результат создания Drive upload.** Ранее после потери ответа на POST повтор делал ещё один POST без закреплённого ID. Минимальное воспроизведение на исходном загрузчике дало `sessionCreates: 2`, `preallocatedDriveId: null`. Это доказывает риск второго файла, но не доказывает, что именно так произошёл сбой в продакшене. Теперь ID получают через `files.generateIds` до создания файла, сохраняют до первого POST и используют повторно. После потерянного окончательного ответа проверяют тот же ID. Журнал не содержит OAuth-токены, resumable URL или байты файлов. Упавший Firestore commit повторяется с тем же ID материала. После F5 нужно заново выбрать те же файлы; уже подтверждённые загрузки используются повторно. Явная команда «Новый материал» начинает отдельную публикацию.
2. **Потеря входа при закрытии вкладки.** В архиве использованы `browserSessionPersistence` и sessionStorage. Теперь Firebase использует `browserLocalPersistence`, а действующий кратковременный Drive grant сохраняется в хранилище этого браузера с владельцем и исходным сроком действия. F5/повторное открытие не продлевают срок. Просроченный доступ удаляется, состояние Drive меняется на «обновить разрешение», вход на сайт сохраняется. SDK Firebase обновляет свой сеанс; Drive access token не становится Firebase refresh token. Приложение не получает серверный offline refresh token и не обещает бессрочный Drive-доступ. Google может потребовать жест пользователя и повторное согласие. На общем устройстве нужно выйти.
3. **Неточная диагностика reader.** Worker отвечал `DRIVE_FILE_PENDING` при любом неуспешном ответе Drive. Теперь отсутствие файла, запрет доступа и недоступность upstream различаются: `DRIVE_FILE_PENDING`, `DRIVE_READER_FORBIDDEN`, `DRIVE_READER_UNAVAILABLE`, с безопасным `upstreamStatus`. До передачи файла проверяется доступ reader к настроенной папке через защищённый `/api/admin/readiness`. Доступ reader к конкретному новому файлу дополнительно проверяется `/api/admin/verify` после загрузки.

Исправление `Window.fetch` через `Reflect.apply` сохранено и проверено в тесте receiver и настоящем Chromium. Новых вызовов native fetch с receiver загрузчика нет. Worker сохраняет `redirect: manual`; браузерная загрузка не получила глобальную замену redirect.

## Что изменено в интерфейсе

Полностью заменены `web/admin.html` и `admin.css`: спокойная светлая студия с постоянной навигацией, одним основным действием, отдельной библиотекой и редактором Telegram. Название берётся из имени файла, остаётся редактируемым. Данные автора/релиза не выдумываются. Есть предпросмотр настоящего локального аудио/видео, обложки, даты и видимости. На узком экране предпросмотр располагается перед кнопкой публикации. Выход доступен и на мобильном.

Библиотека показывает обложку, название, дату, статус, аудиоплеер, редактирование и скрытие. Для скрытого аудио доступен защищённый owner-preview с Firebase ID token в заголовке, без токена в URL и без публичного кеширования. Оригинал и метаданные сохраняются атомарно до необязательного кодирования MP3; ошибка дополнительных качеств не отменяет публикацию оригинала. Кодирование по умолчанию выключено и доступно позже.

Telegram использует прежний multipart-механизм Worker (`sendPhoto`/`sendVideo`), create-only журнал и отдельные результаты по каналам. Интерфейс показывает только два Telegram-канала. VK не настраивался и не является обязательным для выбранной Telegram-only конфигурации. Есть вложение без Drive, локальный предпросмотр, проверка подписи, явная отправка, история. Повтор использует неизменяемый снимок исходного запроса; `failed` и `unknown` не смешиваются. Сервер не повторяет отправку для уже занятого requestId. Лимиты исходников сохранены: JPG/PNG до 10 МиБ, MP4 до 20 МиБ, подпись со ссылкой до 1024 символов.

## Версии и обновление

Сборка выдаёт `public/build-manifest.json`: релиз, fingerprint ресурсов, признак draft и SHA-256 файлов админки, публичной конфигурации и карты медиа. Изменение конфигурации также меняет fingerprint; дополнительный quality-worker получает ту же версию в URL. Все её модули получают общий fingerprint в URL. `/health` Worker выдаёт релиз. Загрузка блокируется с понятным сообщением при несовпадении версии сервиса.

Новая команда `npm run verify:live` читает health, манифест и реальные байты опубликованных HTML/CSS/JS, сравнивает SHA-256 с локальной production-сборкой. Она проверяет файлы, а не просто строку версии. `--worker-only` проверяет Worker перед публикацией Hosting. Команда не изменяет данные и не заменяет E2E-проверку владельца.

## Что ещё нельзя подтвердить

**Я не могу это подтвердить:** успешную новую загрузку в реальный Drive владельца, наследование reader-доступа именно новым файлом, сохранение в рабочий Firestore, появление/воспроизведение этой песни на публичном сайте, реальное восстановление Google OAuth в пользовательском браузере, реальную доставку Telegram-вложения и почты, а также совпадение текущего продакшена с архивом.

Нужны рабочие настройки и авторизации на компьютере пользователя. После команд из `UPDATE-WINDOWS.txt` владелец должен загрузить выбранную им реальную MP3/WAV с обложкой, проверить публичную страницу и F5. Для Telegram он сам выбирает текст, файл и канал и явно нажимает отправку. При ошибке достаточно этапа, HTTP/безопасного кода и номера релиза; не нужны токены, private key или полный HAR. Проверка писем и домен отложены, исходное задание по ним не расширялось.

Сохранение черновика облачной среды не является публикацией сайта или самой среды. В черновик добавлены только нужные домены для чтения сайта/Worker/CDN Firebase, а также воспроизводимые команды установки и локального запуска. Сетевые изменения в текущем runtime пока не применены.

## Дополнение: Hosting emulator на Windows

В выводе пользователя обе проверки Hosting упали: редирект вернул 404 вместо 302,
а CSS — без `X-Content-Type-Options: nosniff`. Причина воспроизведена в установленной
цепочке Firebase CLI 15.33.0 → Superstatic 10 → glob-slash: `path.join/normalize`
превращает URL-шаблон `/media/:id/:name` в `\media\:id\:name`, а `**` — в `\**`.
Движок перестаёт сопоставлять редиректы и заголовки.

Добавлен `tools/hosting-emulator.cjs`. Он задаёт POSIX-нормализацию URL через
экспортируемую `glob-slash.normalize` только в отдельном процессе Hosting emulator.
Файлы зависимостей, продакшен-конфигурация, аутентификация и TLS не изменяются.
Обёртка отказывается запускать команды публикации и другие эмуляторы. npm-команда
`test:hosting` теперь запускает эту обёртку.

Регрессионный тест использует настоящий HTTP-сервер Superstatic: сначала включает
Windows-нормализацию и получает те же 404/отсутствующий nosniff, затем применяет
исправление и проверяет 302, сохранность ID/параметра download и nosniff.
Проверено: регрессия, все 73 unit/integration теста и 2 проверки Firebase Hosting
emulator проходят в облачной Linux-среде. Это воспроизведение Windows-семантики,
а не утверждение о запуске Windows OS; завершающий запуск на компьютере пользователя
ещё требуется. Аудиотест также требует установленного ffprobe; инструкция Windows
дополнена его установкой. Исходники сайта и Worker этим дополнением не менялись.
