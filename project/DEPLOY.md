# Запуск подготовленного проекта

Код подготовлен 27 октября 2026, зависимости и требование Node.js уточнены 28 октября. Этот архив не является публикацией сайта. Текущий сайт, DNS, тарифы и аккаунты при подготовке не менялись. Все команды выполнять из `project` на Node.js 24.12.0 или новее. Для эмулятора Firestore нужна Java 21.

## Проверка без публикации

```bash
npm ci
npm run configure -- --init
npm run doctor
npm test
npm run test:rules
npm run test:hosting
npm run test:runtime
npm run bundle:worker
npm run build -- --draft
npm run check
```

`configure --init` создаёт локальные `settings.json`, `worker/wrangler.jsonc` и `credentials/worker-secrets.json`. Существующие параметры и секреты сохраняются; новые случайные `FORM_SECRET` и `MAIL_RELAY_SECRET` генерируются только при их отсутствии. Команда не создаёт аккаунты и ничего не публикует. Токен Telegram из рабочей сессии не входит в архив: на другом компьютере его нужно ввести в локальный файл секретов. При перевыпуске заменить значение в `credentials/worker-secrets.json` и затем повторить загрузку серверных секретов.

`doctor` проверяет только локальную конфигурацию, не обращается к внешним сервисам и не выводит значения секретов. Отчёт — `deployment-readiness.json`. Для использования в автоматической проверке: `npm run doctor -- --strict` возвращает ненулевой код, пока не заполнены обязательные параметры. Сохранённый в архиве отчёт относится к среде подготовки; после распаковки всегда запускать проверку заново.

`bundle:worker` компилирует сервер через Wrangler с `--dry-run`. Сборка лежит в `build/worker`; никакого размещения в Cloudflare эта команда не выполняет. `test:runtime` запускает настоящий локальный workerd, проверяет health/CORS и отказ в неавторизованной отправке, затем останавливает процесс. Публикации и письма не отправляются. Это не визуальная проверка админки.

## Что заполнить при подключении сервисов

| Параметр | Где задаётся |
| --- | --- |
| HTTPS-адрес будущего Worker | `npm run configure -- --worker-origin https://ВАШ-WORKER.workers.dev` |
| Публичный ключ Google Picker | `npm run configure -- --picker-api-key ПУБЛИЧНЫЙ_КЛЮЧ` |
| Публичный ключ Turnstile | `npm run configure -- --turnstile-site-key ПУБЛИЧНЫЙ_КЛЮЧ` |
| Числовые ID сообществ VK | `npm run configure -- --vk-troika-id ЧИСЛО --vk-eduard-id ЧИСЛО` |
| Ключ отдельного читателя Диска | `credentials/drive-reader.json` |
| Токены Telegram/VK и секрет Turnstile | `credentials/worker-secrets.json` |

Файлы в `credentials`, `.dev.vars`, рабочие настройки и ключи исключены из Git и архива. Не помещать их в `public`. Пример структуры секретов без значений:

```json
{
  "FORM_SECRET": "случайное значение из configure --init",
  "MAIL_RELAY_SECRET": "случайное значение из configure --init",
  "TURNSTILE_SECRET": "секрет Turnstile",
  "TELEGRAM_BOT_TOKEN": "токен messagesed_bot",
  "VK_TROIKA_ACCESS_TOKEN": "токен с доступом к стене ТРОiКА",
  "VK_EDUARD_ACCESS_TOKEN": "токен с доступом к стене Эдуарда Шилова"
}
```

При сохранении секретов использовать реальные значения, сохраняя сгенерированные `FORM_SECRET` и `MAIL_RELAY_SECRET`. Два VK-токена могут быть заменены общим `VK_ACCESS_TOKEN`, если он имеет доступ к обеим стенам. Код не создаёт приложения VK и не выдаёт им права; доступ API нужно подтвердить при подключении. Для Диска подготовлен `reader-access-plan.json`. Пользователь выбрал доступ читателя к корневым папкам; вложенные объекты наследуют этот доступ. Локальная проверка подтвердила чтение метаданных корня, содержимое медиа ещё нужно проверить. Проверка блокирует использование широкого ключа `firebase-adminsdk-*` в Worker; фактические права читателя проверяются отдельно при выдаче доступа.

Бот `@messagesed_bot` и право публикации уже проверены в двух каналах. Их ID внесены в конфигурацию: `telegram_1` — Эдуард Шилов, `telegram_2` — ТРОiКА. Telegram-приглашения не публикуются в Hosting. Отчёты без токена: `telegram-bot-check.json`, `telegram-channel-access-check.json`.

```bash
npm run deploy:worker -- --apply
npm run secrets:worker -- --apply
npm run smoke
```

Загрузка секретов передаёт JSON через stdin, не через аргументы командной строки, и не выводит ответы провайдера с возможными чувствительными данными. Она обновляет только перечисленные значения; удаление секретов этой командой не реализовано. `smoke` выполняет только чтение: health, CORS, отказ анонимному посетителю в доступе к публикациям и HEAD одной аудиозаписи. Успех не подтверждает реальную доставку письма или отправку поста.

5. Обновить правила Firestore из `firestore.generated.rules`, предварительно повторив `npm run test:rules`. Для подготовленного инструмента `tools/deploy-firestore-rules.cjs` нужен закрытый ADC-файл и переменная `GOOGLE_APPLICATION_CREDENTIALS`. Сначала запустить без `--apply`, затем с `--apply`; инструмент проверит ранее опубликованный ruleset и сохранит подтверждение нового исходника в `firestore-deployment.json`. Доступ к пользователям Firebase для этой операции не экспортировать. Каталог уже импортирован: повторный импорт не нужен.
6. После подтверждения актуальных правил выполнить `npm run deploy:hosting -- --apply`. Эта команда проверяет локальные параметры, собирает сайт, проверяет ссылки и сверяет подтверждённый SHA правил. Она публикует только Hosting в `eduard-shilov-site`. Без `--apply` остаётся планом.
7. На временном Hosting-домене проверить настоящий Google-вход владельца, загрузку небольшого материала, скрытие/публикацию, Range-перемотку и мобильный интерфейс. Тест письма и тестовый пост отправлять отдельно с выбранным текстом и получателями. Эти реальные проверки пока не выполнялись.
8. Подключение своего домена и смену DNS выполнять после проверки временного адреса. Текущий сайт сохраняется до согласованного переключения. До переключения откат — оставить прежний сайт и DNS; после переключения — вернуть записи из `dns-before-migration.json`. Для правил сохранён предыдущий ruleset в отчёте. Не выполнять повторный импорт каталога при откате.

## Исправление redirect в Worker

28 октября публикация Worker версии `12e679ca-09f2-4bf6-b1bf-9d8ddc3f54e9` и загрузка секретов завершились на компьютере пользователя. Live smoke выявил 503 медиамаршрута. HTTP-модуль исправлен на manual; каждый вызывающий обработчик отвергает неподходящий HTTP-статус, перенаправления не выполняются автоматически. Явный follow существующего почтового relay сохранён. Новая runtime-проверка выполняет полный путь медиа с тестовыми провайдерами и настоящими Request/WebCrypto/Range/HEAD, без ключей пользователя и внешних отправок. Исправленную версию ещё нужно опубликовать и выполнить live smoke.

## Обновление студии — 29 октября

Ошибка Illegal invocation исправлена в DriveUpload: native fetch вызывается с globalThis как получателем. Drive scope запрашивается в исходном Google-входе, токен из credential используется для проверки выбранной ранее папки; отдельное принудительное prompt:consent убрано. Переаутентификация того же владельца не сбрасывает текущий план загрузки. 401 показывает подключение, после него загрузка возобновляется с той же сессией.

Длинные (>15 минут, если браузер определил длительность) и большие (>100 МБ) дорожки автоматически идут как оригинал без обработки в браузере. Обложки опубликованных материалов и оригиналы запрашиваются у Worker, а не у Hosting. Файлы студии и загрузчик имеют версию URL studio-2 для обхода старого кэша.

Браузерная визуальная проверка и реальная авторизация/загрузка для новой админки остаются неподтверждёнными; модульные сценарии используют подменённые внешние границы.

## Упрощённая админка и вложения Telegram — 29 октября

Разделы: Добавить материал, Мои материалы, Публикация в Telegram. Светлая тема и прямые подписи вместо боковой панели. browserSessionPersistence сохраняет Firebase-вход при обновлении вкладки. Короткий Drive access token, UID и исходный срок действия сохраняются в sessionStorage; восстановление не продлевает срок. Сессия удаляется при выходе, смене владельца и истечении. При обновлении вкладки живой токен проверяется без нового Google popup. Постоянный серверный refresh token не создаётся.

Оригинал с обложкой сначала атомарно сохраняется в каталоге. Дополнительные качества создаются после этого; сбой кодирования не блокирует уже сохранённую песню. Ошибки содержат этап, HTTP-статус и допустимый код Google, без токенов. При задержке доступа читателя к свежему файлу проверка повторяется до трёх раз, без повторной загрузки файла. Точный сбой загрузки в браузере пользователя ещё не воспроизведён в его сеансе.

Вложения передаются из браузера прямо в защищённый Worker как multipart. Авторизация владельца проверяется до чтения тела. Тело ограничено 20 МиБ плюс 64 КиБ заголовков/метаданных; фото дополнительно ограничено 10 МиБ. Поля и MIME проверяются, SHA-256 вычисляется сервером. В историю попадают тип, имя, размер и хеш, но не байты файла. Повтор того же requestId с другим файлом отклоняется. sendPhoto/sendVideo вызываются только для выбранных Telegram-каналов; VK с вложением отклоняется. Новых сервисов и ключей не требуется.

Для обновления нужны Worker и Hosting. Правила Firestore не изменялись; действующая схема допускает закрытые метаданные вложения. Файлы JS/CSS студии используют версию studio-3. Полная браузерная проверка новой версии и отправка реальных вложений пока не выполнены.

```cmd
npm run deploy:worker -- --apply
npm run smoke
npm run deploy:hosting -- --apply
```

Выполнять последовательно, останавливаясь при ошибке. После обновления войти один раз и проверить F5 в той же вкладке. Новая песня проверяется маленьким файлом с обложкой; реальную отправку в канал запускать только выбранным пользователем текстом и файлом.
